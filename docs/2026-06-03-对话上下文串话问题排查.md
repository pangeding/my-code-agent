# 对话上下文串话问题排查

## 问题描述

用户反馈：使用 `make run` 启动助手后，第一次问的是写小说相关的问题。几天后重新启动 `make run`，问的是情感问题，但 AI 的回答仍然扯到写小说，出现了"串话"现象。

## 排查分析

### 代码审查结果

审查了以下核心文件：

1. **cmd/main.go** - 主程序入口
2. **internal/llm.go** - LLM 客户端实现
3. **internal/config.go** - 配置加载
4. **internal/tools.go** - 工具函数定义

### 问题根因

**对话历史（messages）没有被持久化存储，但也正因如此，不存在跨会话的上下文污染。**

具体分析：

1. `cmd/main.go:34` 定义了 `var messages []openai.ChatCompletionMessageParamUnion`，这是一个局部变量
2. 每次执行 `make run`（即 `go run ./cmd/`）时，都会启动一个全新的进程
3. `messages` 变量会被重新初始化为空切片（只包含 system prompt）
4. 进程结束后，所有对话历史都会被销毁

**因此从代码逻辑上讲，不应该存在跨会话的"串话"问题。**

### 可能的原因

1. **AI 服务提供商侧的问题**：某些 AI API 提供商可能会基于用户 API Key 对对话进行缓存或上下文关联，特别是当使用了支持"project"或"conversation tracking"的服务时

2. **System Prompt 污染**：如果 `.env` 中的 `AI_SYSTEM_PROMPT` 包含了与之前写小说相关的内容，可能会影响后续对话

3. **模型自身的偏差**：LLM 可能基于之前的对话模式（即使在不同会话中）产生了倾向性，这种情况在某些有状态 API 中可能出现

4. **用户可能使用了带有 conversation ID 的 API**：如果 API 支持 conversation tracking 且使用了相同的 conversation ID

### 建议的解决方案

1. **检查 `.env` 文件**：确认 `AI_SYSTEM_PROMPT` 是否包含写小说相关的指令
2. **确认 API 特性**：查阅所用 AI API 的文档，确认是否有服务端上下文缓存机制
3. **增加会话隔离**：如果 API 支持，确保每次启动使用不同的 session/conversation ID

## 代码架构总结

当前程序的对话流程：
1. 启动时创建空的 `messages` 列表
2. 添加 system prompt（如果配置了）
3. 循环读取用户输入
4. 将用户消息追加到 `messages`
5. 调用 LLM API
6. 将 AI 回复追加到 `messages`
7. 如果有 tool call，执行后继续调用 LLM

**关键特性**：
- 所有对话历史保存在内存中（`[]openai.ChatCompletionMessageParamUnion`）
- 没有任何持久化机制（无文件存储、无数据库）
- 进程重启后对话历史完全清空
